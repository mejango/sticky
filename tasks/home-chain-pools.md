## Plan refinement

- **Objective:** Each new Sticky pool has exactly one selected home chain. Its shares, backing, snapshots, reward accounting and redemption stay there, while qualified V6 reward sources can fund it from other chains. Success is a single-target launch and explicit, immutable destination routing with no recurring Safe authority.
- **System fit:** Select and verify the home-chain asset, prepare one launch, confirm the receipt-bound pool identity, derive its reward receiver and destination-bound hook, authorize source splits, queue reserves, perform permissionless delivery, observe finality/claim/settlement, and verify holder collection. Existing core, Sticky pool accounting, receiver/distributor and shared wallet/recovery owners remain responsible for their current layers. Regressions and deployment evidence enforce each boundary.
- **Reuse and simplicity:** Reuse the existing single-chain deployer, one-target SDK launch path, chain/project keys, receiver factory, collector accounting and fee helper. Configure one collector family per destination chain using immutable constructor data; do not add an administrator, per-pool registry, new factory or packed split encoding. Keep shared SDK multichain capabilities used by other clients. Remove Sticky's grouped-pool semantics rather than creating a parallel launch flow.
- **Evidence and unknowns:** At plan start, the create UI defaulted all available chains and prepared independent projects under a shared launchId, home/sibling views grouped those pools and summed supplies, contract accounting was already local, and the collector destination was constant 1. The pinned JBP6/REV native fixtures prove Ethereum-to-L2 and L2-to-Ethereum routes, not L2-to-L2 connectivity. Verify current route/dependency state for any release; no blanket all-source/all-home delivery claim. A transferable token can be wrapped externally, but wrappers do not become canonical Sticky reward ledgers.
- **Verification:** Enforce exactly one Sticky launch target at preparation, persisted-plan validation and the wallet boundary; prove receipt/chain identity and no cross-pool supply aggregation. Contract tests must prove non-Ethereum local settlement, real qualified remote delivery, wrong-peer rejection, destination-family isolation, unchanged group interpretation and same-address parity within each destination family. Re-run custody/refund regressions, strict build/style/static checks, affected client/SDK suites and finalized deployment rehearsals. Review the separate tooling change before proposal collection; published runtime/artifact identity and onchain receipts remain deployment gates.
- **Resource budget:** Root integrates; separate contract/deployment and client/SDK owners can work in parallel after this plan. Serialize Forge/RPC verification. Do not rerun unchanged pool-contract audits or add migration machinery for the user's unused launch flow. Refine before introducing multi-hop transport or changing shared SDK contracts. Existing deployment predictions must be regenerated when constructor/initcode changes.

## Decisions

1. **Pool identity:** use `(homeChainId, shareToken)` and the existing chain/project identity. Same names, underlying assets, addresses or launch metadata on another chain do not establish one pool. No global singleton-per-underlying registry is needed.
2. **Launch:** choose one supported home chain. Resolve and verify the underlying there; a chain-qualified token/project input must not silently become another chain's token. The new Sticky launch planner and restored-plan execution must reject multiple targets. Reuse the shared launch/wallet lifecycle with one target; existing one-element target/chain arrays are sufficient, so this does not require a new generic SDK launch format. Retain recorded transaction hashes, quotes and Safe proposal evidence for read-only recovery even when a stale multi-target plan cannot send again.
3. **Collector destination:** make `DESTINATION_CHAIN_ID` an immutable constructor parameter. The Ethereum-targeted collector has one address shared across participating source chains; a Base-targeted collector has a different address shared across its sources, and so on. Deploy all four families together for each testnet or mainnet environment so a later pool launch needs no contract deployment. The UI derives the correct family from the selected pool's home chain.
4. **Split encoding:** preserve `hook = verified collector for the home chain`, `beneficiary = home-chain Sticky share token`, `split.projectId = existing reward group`. No new encoding in the uint64 group field. The delivery caller selects only a qualified route and amount, never a new destination.
5. **Local versus remote:** settle only when the executing chain equals the collector's destination. Remote send must require a registered, usable sucker whose peer is that destination. Retain exact allowance, accounting, nested receipt, fee/refund and rollback invariants. A collector address namespaces destination custody, so the existing project/token/group pending keys remain sufficient.
6. **Supported routes:** this phase supports direct, qualified routes only. The tested native topology is an Ethereum hub. OP-to-Base needs an independently verified direct route or a separately designed permissionless relay through Ethereum. Sending to an intermediate collector is not a relay: plain token arrivals create no attributed queue. Reject unsupported source/home combinations during setup; do not promise full mesh routing or fall back to Ethereum.
7. **Product boundary:** show a pool's home chain separately from its reward source chains. Pool supply, backing, rewards and redemption belong to the selected pool. Portfolio pages may show positions across chains as distinct pools. Existing independent deployments remain distinguishable if discovered; no new bespoke migration system is planned.

Add missing receiver, source collector and fee payer interfaces; reuse existing Sticky and Juicebox interfaces elsewhere.
