## Design decisions

### Split and custody

Use `hook = shared collector`, `beneficiary = Ethereum Sticky share-token address`, `split.projectId = reward group` (0 for JBX). The context's project ID identifies the source reward project. Authenticate the current controller through the collector's canonical DIRECTORY, require RESERVED_TOKENS group, this hook and zero native value, and match any nonzero source token through canonical TOKENS. A zero token denotes already-transferred credits even if an earlier split deployed the ERC20 after the controller cached its token choice. The receiver factory owns destination/group validation and prediction; source chains do not require the Ethereum share token to exist locally.

`pendingOf(sourceProjectId, stickyToken, groupId)` attributes accepted custody; `totalPendingOf(sourceProjectId)` bounds aggregate liabilities. ERC20 receipt credits the measured increase in combined project custody (TOKENS.totalBalanceOf), less the increase in aggregate pending liabilities accepted by nested callbacks during the transfer. This excludes nested same-project receipts from the outer credit and handles credits plus ERC20 under one custody unit. Credits have already arrived from core before the callback; authenticate and book the amount only if total project custody covers existing plus new liabilities. Permissionless delivery claims held credits into the project's eventual ERC20 before spending. Unattributed token/credit donations cannot be assigned to a caller or drained as another bucket.

Acceptance is intentionally allowed during outbound fee processing and during other valid acceptance callbacks, which may distribute more reserves. A transient acceptance depth blocks every outbound operation until all nested receipts finish; it never rejects a valid incoming callback merely because another receipt is active. Snapshot combined custody and aggregate pending before a token transfer, then subtract nested liability growth from the received delta; aggregate pending can only increase while outbound operations are blocked. Contextual checks reject custody decreases or a delta smaller than nested receipts. Outbound reentrancy is otherwise prohibited, and selected liabilities are debited before external calls. Callback allocations stay queued. No funding, bridge preparation, route admission or fee payment occurs in the acceptance callback.

### Delivery API

- `settle(sourceProjectId, stickyToken, groupId, amount)` on Ethereum: debit a positive amount from that bucket, materialize source ERC20 custody, transfer to its predicted receiver, and call the existing factory settlement atomically. Existing receiver inventory also settles under its established rule.
- `send(sourceProjectId, stickyToken, groupId, amount, sucker, backingToken)` on another chain: debit a positive partial amount, use a registered sending-enabled route with Ethereum peer, matching canonical registry/directory/tokens and an enabled nonemergency backing mapping. Predict the fixed receiver, quote the chosen primary backing terminal with sucker holder/beneficiary, approve exactly amount, prepare one leaf, clear allowance, submit through the fee helper and prove that exact new index is in the sent root. Any failure restores the bucket and principal.
- Allow fresh zero backing quotes because sucker remint count is independent of backing. The bound is gross minus the maximum standard protocol fee in backing-token atoms. Custom caller-sensitive cashout hooks can make this conservative preview fail closed; queued tokens remain retryable.
- Caller selects a replacement registered route if one retires. Partial amounts handle upstream uint128 capacities. No project1/3, source-chain or native-backing restriction is embedded in runtime.

### Fee custody

One child is permanently callable only by its parent. It takes the validated sucker and backing token dynamically; derives that sucker's fee token from its canonical TOKENS and FEE_PROJECT_ID. Require a deployed fee ERC20 when the registry fee is positive, to prevent untracked fee credits. When the registry fee is zero, core skips fee payment, so the absence of that ERC20 must not prevent transport; measure fee-token deltas only when the token exists. Caller value covers at least registry fee, with any excess supplied as transport budget. Native OP/Base/Arbitrum sends normally use exactly registry fee; native-payment CCIP routes may need excess. LINK transport funding is not provided.

The child cannot pull principal from the parent. Snapshot fee-token donations, submit, return only the same-call positive delta, and claim fresh retained registry-fee and transport-payment refunds directly to the original caller. Reject either retained credit before the send and any residual after refund. No receive handler or general rescue is introduced; forced ETH/preexisting donations remain excluded. A rejecting caller can revert only their own attempt.

### Deployment and authority

Constructor bindings are `(registry, tokens, receiverFactory)`; derive DIRECTORY from registry. Ethereum destination ID is constant1, source chain is read at runtime. Same initcode/arguments/salt through the canonical CREATE2 factory yields the same hook address. Extend the existing deployment owner and immutable verification rather than bypass them; verify the child address/binding as part of its parent. Keep prior singleton addresses and artifacts intact. Do not record unexecuted deployments as live.

## Receipt refinement from adversarial review

A single rejecting inbound lock would let a custom project token trigger another project's permissionless reserved distribution during transferFrom and cause the controller to burn the rejected allocation. Permit valid nested receipts instead. Combined project-custody delta minus nested aggregate-liability growth isolates each receipt with no new token ledger; the transient depth prevents every debit during that measurement. A zero-token context is legitimate after the controller cached credits but an earlier split deployed the ERC20. Tests must cover both cases against actual catch-and-burn behavior and verify nested receipts are counted once. This updates the receipt architecture before its implementation; the six refinement fields and remaining authority/verification gates still apply.

Zero-fee route refinement: core JBSucker skips fee-terminal payment when the registry fee is zero. Allow that route even before its fee ERC20 exists; keep both native refund ledgers checked and claimable. Positive fees still require a deployed fee ERC20. Cover both paths with unit regressions; canonical four-chain fee tokens already exist.
