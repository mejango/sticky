# Architecture

## Purpose

`@bananapus/sticky-v6` lets holders of an ERC-20 lock it into a permanently configured Juicebox V6 project in exchange for Sticky shares of that project's backing, while recording weekly tranche amounts, their latest addition timestamps and a per-holder streak that off-chain reward programs can trust.

The value the system protects is the backing allocated to outstanding shares. A holder or their authorized operator can redeem through the terminal under the launch-time cash out curve and applicable fees. Maximum tax returns zero even when redeeming the whole supply. These guarantees depend on the configured core contracts and a supported underlying token.

## System Overview

The package owns a deployer that launches locked projects, a singleton data hook that prices issuance and does position accounting, a per-project price feed that gives core the exact issuance denominator, and a per-project share token. It composes `nana-core-v6` for everything economic: `JBMultiTerminal` custodies the underlying tokens, `JBController`/`JBRulesets` enforce the eternal ruleset, `JBPrices` routes the feed, and `JBTokens` mints and burns the share token. Rewards go through `StickyDistributor`, a subclass of `JBDistributor` from `nana-distributor-v6` that keeps the token distributor's vote-checkpoint allocation as group 0 and adds funder-chosen tenure groups weighed by the hook's tranches, with two optional helpers: an opt-in compounding adapter and cross-chain reward receivers.

### One home chain per pool

A pool is identified by `(homeChainId, shareToken)` and its chain/project identity. Shares, backing, snapshots, reward accounting and redemption stay on that home chain. A pool with the same name, underlying asset, address or launch metadata elsewhere is an independent pool; its supply must not be added to this pool's supply. Portfolio views can list distinct positions across chains without merging their accounting. An external wrapper of transferable shares does not create another canonical Sticky reward ledger.

Sticky launch preparation and executable saved plans require exactly one supported home chain. Chain-qualified asset input remains bound to that chain. Multi-target saved plans retain receipts and transaction history for inspection, but cannot execute by silently discarding targets. Other clients retain the SDK's general multichain launch primitives. The [home-chain plan](tasks/home-chain-pools.md) owns this product boundary and its implementation gates.

## Core Invariants

- **Backing-priced issuance, never dilutive**: a deposit of `A` underlying atoms issues `floor(A × S / E)` share atoms, where `S` is the outstanding supply and `E` is the backing owned by shares. `StickyHook.beforePayRecordedWith` returns `S` as the weight and `StickyPriceFeed` returns `E` as the price, so core computes the ratio without rounding an exchange rate first. The after-pay callback re-derives the expected count from the authenticated snapshot and rejects any mismatch, any intervening supply or backing change, and any positive payment that issues zero shares.
- **Orphaned backing is excluded forever**: backing present while supply is zero has no owner. The next positive stake stores it as `orphanedBalanceOf` and both the feed and the cash out hook subtract it. Nobody, including the deployer, can withdraw it.
- **No discretionary withdrawals**: payout limits and surplus allowances are zero, and terminal migration and terminal changes are disabled. Cash outs and core fee processing account for value leaving the project. Donations via `addToBalanceOf` and retained cash out tax raise backing per share.
- **Permanent project configuration**: the deployer owns the project NFT and exposes no call to queue another ruleset. Zero tax makes gross redemption proportional; tax below the maximum uses the Juicebox curve; maximum tax returns zero. Applicable terminal fees are separate. Core's privileged omnichain operator remains a dependency trust boundary.
- **Independent exits**: bootstrap issuance must reach `1e12` share atoms, but burns can leave any supply. Another holder's dust does not force a holder to retain shares. Very small remaining supplies can make issuance too coarse for a later deposit to pass the rounding guard.
- **Share book equals token balance**: at completed transaction boundaries, `stakedBalanceOf` equals the holder's ERC-20 balance. The token reports every positive burn and transfer to the hook from its `_update` path, and refuses to move tokens out of an address whose balance and book disagree, which closes the window between the terminal's mint and the after-pay callback.
- **LIFO with timestamp preservation**: exits consume tranches newest-first; a split tranche keeps its original timestamp. Cumulative tranche balances let a partial exit binary-search its retained tail. Each consumed tranche debits the epoch bucket it joined in, and same-week joins merge into the newest tranche, so an exit's work is bounded by the distinct weeks it consumes and incoming dust cannot make it unbounded.
- **Buckets sum to supply**: `netStakedIn[projectId][epoch]` is credited when tokens join a position and debited at the consumed tranche's original epoch, so the buckets always sum to the staked balances. Because tranches only ever join the current week, every bucket older than the current week is frozen except for exits, which is what lets a tenure round's denominator be read once at funding and its claims be read lazily from live tranches.
- **Streak monotonicity**: `streakStartOf` is set only on a 0→non-zero balance transition and cleared only on a non-zero→0 transition. Staking more never moves it.
- **Tranche age stays with the deposit**: soulbound tokens revert transfers outright; transferable tokens route every positive non-self transfer through `recordTransfer`, which consumes the sender's newest tranches and adds the moved tokens to the receiver's current-week tranche or a fresh one. An existing recipient's holder streak continues, so duration-weighted amounts must use tranche ages.
- **Votes follow ownership**: every holder is self-delegated on first receipt and `delegate`/`delegateBySig` revert. At a past block, votes equal that holder's balance at the same block, and past active votes equal past supply. Snapshot ownership is independent of tranche age and can include temporarily held shares; group 0 uses it, tenure groups do not.
- **State-changing callbacks are gated**: after-pay and after-cash-out callbacks accept only a terminal of the project per `JBDirectory` and reject forwarded native value; burn and transfer reports accept only the project's registered token; granters and token registration accept only the deployer. The before-recording data hooks are public views used by core and previews.

See [INVARIANTS.md](./INVARIANTS.md) for the complete verification checklist and [RISKS.md](./RISKS.md) for its limits.

## Modules

| Module | Responsibility | Notes |
| --- | --- | --- |
| `StickyDeployer` | Launches sticky projects with the locked eternal ruleset; deploys the share token with CREATE2 under a launcher- and configuration-bound salt, attaches it and the price feed; permanent owner of every project it launches | Immutable; creates `StickyHook` in its constructor; its only external transaction is `deployStickyFor`; `predictStickyTokenOf` reproduces a launch's token address |
| `StickyHook` | `IJBRulesetDataHook` + `IJBPayHook` + `IJBCashOutHook` singleton keyed by project ID; issuance pricing, orphaned-backing exclusion, exact balances, LIFO tranches, streaks, granter and trusted-sender gates | Immutable; receives no funds (hook specifications carry `amount: 0`); no owner |
| `StickyPriceFeed` | One per project; returns share-owned backing in the terminal's cached accounting precision as the issuance denominator, or one unit while supply is zero | Registered under a distinct synthetic base currency; the after-pay check rejects issuance mismatches, including an incorrect fallback price |
| `StickyToken` | ERC-20 shares, soulbound or transferable, with checkpointed locked self-delegation; reports burns and transfers to the hook | One per project, bound via `canBeAddedTo`; mint/burn only by `JBTokens` |
| `StickyDistributor` | Round-based reward distribution with linear vesting; group 0 weighs vote checkpoints at the round's snapshot block, tenure groups weigh the stake held in tranches created within a week window before the round started | Subclass of `JBDistributor` bound to the hook; loans disabled; splits carry the group in `split.projectId`; 20,515-byte runtime |
| `StickyAutoStick` | Opt-in, keeper-executable compounding of a holder's vested underlying-token rewards from the caller's chosen reward groups back into the same position | Immutable; nothing caller-provided beyond project, holder, and groups; quotes the terminal and enforces the quoted minimum |
| `StickyRewardReceiverFactory` | Predicts and deploys one deterministic reward receiver per Sticky token and reward group; `settleFor` deploys it if needed and settles its balance | A shared deployment entrypoint bound to one distributor; rejects groups the distributor rejects |
| `StickyRewardReceiver` | Holds arriving reward tokens for one Sticky token and group and settles them permissionlessly into its bound distributor | Attribution by receiver address; minimal clone of one implementation; no deposit ledger or ordered queue; can receive tokens before deployment |
| `StickySourceCollector` / `StickySourceFeePayer` | Reserved-token split acceptance and attributed custody for one immutable home chain, followed by permissionless local settlement or qualified direct-route delivery there | One shared collector family per home chain; only-parent child isolates caller fee receipts/refunds; no owner, arbitrary calls or rescue |

### Public interfaces

Public declarations, typed getters and events belong in [src/interfaces](src/interfaces/), with concrete contracts retaining errors and execution. The existing Sticky interfaces own each contract's Sticky-specific surface and inherit established protocol interfaces where appropriate. `StickyPriceFeed` uses `IJBPriceFeed`; libraries do not receive parallel interfaces.

`IStickyRewardReceiver` exposes receiver bindings, initialization and settlement. The factory's `RECEIVER` getter uses this interface. `IStickySourceCollector` inherits `IJBSplitHook` and owns the six immutable bindings, pending getters, delivery functions and queue/send/settle events. Its `FEE_PAYER` getter uses `IStickySourceFeePayer`, which exposes the parent binding and fee submission. Public sucker arguments use the existing `IJBSucker` interface; implementations retain narrow concrete casts for fee-registry, fee-project and refund APIs absent from that upstream interface. `IStickyAutoStick` includes its minimum/maximum cooldown getters alongside its existing configuration and compounding API.

These declaration boundaries do not add authority, storage or an ERC-165 registration. Interface refactoring must preserve the six deployed contracts' executable bytecode, public selectors, event topics and behavior. ABI `internalType` metadata can change from a concrete contract to its interface without changing the encoded address type. The collector's new destination constructor argument is a separate behavior change and requires fresh deployment predictions.

### Why a receiver and a factory?

A bridged ERC-20 transfer delivers a token balance to an address without telling Sticky which reward pool should receive it or how it should be weighed. Each receiver's address identifies one Sticky token and one reward group, so arrivals for different pools and weightings remain separate even when they use the same reward asset. Its immutable bindings determine which distributor pool settlement funds. The factory predicts these receiving addresses, deploys the receivers when needed, and provides the shared `settleFor` entrypoint. That deployment role could be folded into another contract, but receiving addresses still need separate pool attribution; sending every arrival to one shared balance would lose it. Settlement forwards the receiver's whole balance of the chosen reward asset, so there is no ordered queue of deposits.

### Shared reserved-token split hook

Each `StickySourceCollector` binds the canonical sucker registry, token registry, receiver factory and a nonzero immutable `DESTINATION_CHAIN_ID`, appended to its constructor arguments; it derives the directory from the registry. One destination family can serve many pools on that home chain. Matching CREATE2 initcode, constructor bindings and salt give that family the same address across its participating source chains. A different home-chain argument produces a different collector address and separate custody. Every source uses `hook = verified collector for the home chain`, `beneficiary = home-chain Sticky share-token address`, and `split.projectId = reward group`. The callback's own `projectId` identifies the reward source; its `groupId` must identify core's reserved-token group. No destination is packed into either group field.

`processSplitWith` authenticates the current source controller and records accepted custody in `pendingOf(sourceProjectId, stickyToken, groupId)`, with aggregate liabilities in `totalPendingOf(sourceProjectId)`. ERC-20 receipt is the increase in combined project custody from `TOKENS.totalBalanceOf`, less aggregate pending growth accepted by nested callbacks during that transfer. Credits arrive from core before the callback and are booked only when combined custody covers the resulting liabilities. A zero-token context still denotes credits when an earlier split deployed the ERC-20 after the controller cached its token choice.

Acceptance performs no reward funding, route selection, preparation or fee payment. This boundary also applies on the home chain so a downstream receiver or bridge failure cannot make the controller burn an otherwise accepted ERC-20 allocation. Credits can be queued before the source ERC-20 is deployed; delivery materializes held credits into that token before spending. Unattributed donations are not another allocation's spending authority. The collector address already identifies the destination chain, so its existing source-project/token/group keys need no extra destination field.

Anyone can deliver a positive partial amount from one pending bucket. `settle(sourceProjectId, stickyToken, groupId, amount)` is available only when the executing chain equals `DESTINATION_CHAIN_ID`; it transfers source project tokens to the predicted receiver and calls the existing factory's settlement in the same transaction. The receiver settles its whole balance of that reward token, including earlier arrivals. On other chains, `send(sourceProjectId, stickyToken, groupId, amount, sucker, backingToken)` authenticates a registered source-project route against the collector's registry/directory/tokens, its peer on the immutable home chain, sending state and non-emergency backing mapping. A caller can choose a valid replacement direct route after another retires, without changing the bucket's home-chain token/group destination.

A selectable home chain does not establish a transport path. Configure only qualified direct source/home routes. The pinned native JBP6/REV topology is an Ethereum hub; OP-to-Base or another L2-to-L2 lane is unsupported without a separately qualified direct route. There is no implicit relay or fallback through Ethereum. Sending ordinary tokens to an intermediate collector does not create a relay because those arrivals have no attributed pending allocation.

Remote delivery quotes the chosen primary backing terminal with the sucker as holder and beneficiary, subtracts the maximum standard protocol fee, grants exactly the selected project-token amount, prepares one fixed-receiver leaf, clears allowance and submits its outbox through the fee payer. The sent count must cover that leaf. A zero fresh backing quote is allowed: the sucker's project-token remint count is independent of backing. The execution-time minimum uses backing-token atoms; it is not a caller-selected market price or destination-token quote. Any preparation, submission, refund or inclusion failure restores the selected liability and custody. Native or mapped ERC-20 backing may be used when the registered route supports it; the rewards themselves remain the source project's token.

Fee processing or an ERC-20 transfer may distribute additional reserves. Valid nested acceptance remains available during another receipt or outbound processing, and those allocations stay queued. Transient acceptance depth blocks every outbound operation until all nested receipts finish, so nested pending growth can be subtracted without an intervening debit. Delivery also cannot reenter an existing outbound operation. The separate `StickySourceFeePayer` is callable only by its creating collector and has no allowance over parent principal. It derives the fee token from the validated route and requires that fee project's ERC-20 when the registry fee is positive; zero-fee delivery can proceed without it. Caller value covers at least the current registry fee, with excess forwarded as transport budget; LINK transport funding is not provided.

When the fee ERC-20 exists at submission entry, the child returns its same-call token increase. It also returns the newly retained source-chain registry fee and transport refund directly to the original delivery caller. It rejects preexisting or residual credit in either source-chain refund ledger. Prior token donations and forced ETH are excluded; a deliberate token donation during submission also enters the returned delta, which authenticates no mint provenance. A rejected receipt or source-chain refund reverts the complete delivery. The child has no native receive handler or general rescue. These checks do not cover asynchronous destination-chain refunds; the native Ethereum-to-Arbitrum collector lane remains unqualified because its retryable excess-fee refund targets the fee child on Arbitrum, where the value is not attributed or recoverable.

The constructor binds canonical dependency addresses; live deployment verification establishes their identities and cross-chain parity. Route registration remains a trust boundary for approved builders and source-project configuration, and the source chain cannot prove that the intended home-chain pool or reward ERC-20 exists. Native finalization, sucker claim, receiver settlement and holder collection remain separate after source submission. [DEPLOYMENT.md](DEPLOYMENT.md#source-collectors) owns setup and verification; the [current plan](tasks/omnichain-split-hook.md) records the shared-hook review and execution gates. The [fixed-route audit](SOURCE_COLLECTOR_AUDIT.md) is historical evidence, not verification of this design.

### Why a per-project price feed?

Core calculates share issuance as `floor(amount × weight / price)`, in the terminal's accounting precision. Sticky supplies outstanding share supply as `weight` through the hook and exact share-owned backing as `price` through `StickyPriceFeed`. Keeping that numerator and denominator separate avoids first rounding an exchange rate and then multiplying a deposit by the rounded result. The feed reads terminal accounting and subtracts orphaned backing; it does not obtain an external market price.

`IJBPriceFeed.currentUnitPrice(decimals)` has no project ID argument, so the singleton hook cannot directly return a different project's backing for each call. Each feed binds the required project and accounting context. The per-project share token could implement this interface instead and save a standalone deployment, but that would add terminal, backing, and pricing responsibilities to the token. The separate feed keeps those responsibilities in a small accounting adapter.

## Data Flow

**Stake**: holder (or granter / trusted sender) → `JBMultiTerminal.pay` → store calls `beforePayRecordedWith` (trust gate, snapshot of supply/backing/orphaned, weight = supply) and `JBPrices` → feed (backing − orphaned) → store records payment and calculates `floor(A × S / E)` → controller and `JBTokens` mint shares → terminal calls `afterPayRecordedWith` with the snapshot as metadata → hook checks the issued count and post-state, stores the orphaned baseline if it changed, merges into the current-week tranche or appends a new one, and starts the streak if the balance was zero.

**Unstake**: holder → `JBMultiTerminal.cashOutTokensOf` → `beforeCashOutRecordedWith` passes the tax rate, count, and supply through and subtracts the orphaned balance from surplus → terminal burns through the controller and `JBTokens` → the token's `_update` calls `recordBurn` → hook consumes tranches newest-first and ends the streak if the balance reached zero → terminal pays the reclaim after applicable fees.

**Voluntary burn**: `JBController.burnTokensOf` follows the same token path, so the book stays exact; the burned shares' backing stays with remaining holders.

**Reward**: funder → distributor `fund` (optionally with a group), a payout or reserved-token split with the group in `split.projectId`, or destination reward receiver → `settle` → distributor `fund` → the current round's pot for that group. For group 0, the first positive funding pins the current round's snapshot block if needed and records the active vote total as the denominator; `poke()` can pin the current and following round. For a tenure group, the first funding of a round records the denominator from the hook's buckets over the window measured back from `snapshotEpochOf(round)`, the week the round started in. Claims read vote checkpoints (group 0) or `stakedBalanceThroughEpochOf` on the holder's live tranches (tenure) and vest over four weekly rounds. Anyone can choose when to settle a receiver, which can change the reward round and its recipients.

**Compound**: enabled holder configuration → keeper `compoundFor`, or holder `stickRewardsFor`, naming the reward groups → collect each group's vested underlying rewards to the holder → pull only the total delivered amount → terminal preview → pay for the same holder. Trust and allowance are separate requirements. The final payment enforces its freshly quoted minimum.

**Reserved reward acceptance**: source controller → authenticated `processSplitWith` on the selected home-chain collector family → accepted ERC-20/credit custody and attributed pending bucket. No bridge, funding or fee call occurs during acceptance. **Home-chain delivery**: caller → debit part of one bucket → materialize source ERC-20 custody → predicted receiver transfer → factory settlement. **Remote delivery**: caller with registry fee and transport budget → validate qualified direct route to the immutable home chain → debit part of one bucket → materialize custody → cashout preview and exact approval → fixed-receiver leaf → child submission/refunds → own-leaf inclusion check → canonical finalization → destination claim → receiver settlement → holder vesting and collection. A reverted delivery restores the bucket and same-transaction effects.

Source project-token counts and credits use core's 18-decimal project-token units. Fee receipt counts use the fee ERC-20's atoms; cashout bounds use the selected backing asset's atoms; registry fees and transport payments/refunds use native wei; outbox indices and counts are unitless. The collector does not compute the destination mint or convert rewards into the Sticky underlying asset.

Decimals: tranche amounts, staked balances, and cash out counts are all in the share token's 18 decimals; issuance and backing use the underlying token's accounting decimals, 0 to 36.

## Trust & Permissions

- No Sticky implementation has an upgrade path or an administrator who can change its immutable bindings. Holders can change their personal trust and auto-stick settings.
- Core still has protocol controls. In particular, `JBController.OMNICHAIN_RULESET_OPERATOR` bypasses owner authorization for queueing rulesets. The canonical omnichain deployer enforces owner/operator permissions before calling core; verify that binding and implementation on each chain. The trusted forwarder and core permission model are part of this assumption.
- `allowSetCustomToken` and `allowAddPriceFeed` stay enabled in the eternal ruleset because the launch transaction needs them; both core calls are owner-gated and the owner is the deployer, which exposes no later call to either.
- Any project can point its own ruleset's `dataHook` at `StickyHook`; the accounting is keyed by project ID and requires a registered token, so a rogue project can only revert its own pays.
- The underlying token is trusted for standard ERC-20 behavior. Fee-on-transfer and rebasing tokens are unsupported; the adapter rejects an unexpected holder-to-adapter transfer delta. A successful factory launch does not certify a token's transfer behavior.
- Reward receiver address parity across chains requires a matching verified factory address and receiver implementation, destination Sticky-token address, and group; receivers are clones of the implementation the factory is bound to, so the factory address fixes it. Read the destination factory's prediction before bridging; no source-chain deployment is required to receive at that destination address.
- Source collector deployment fixes the registry, tokens, directory and receiver factory; every delivered route must agree with those canonical bindings and current registration. Registry-approved builders, source-project peer/mapping configuration, current controller and terminal behavior remain dependency authorities. A registered route is not independent proof of a safe peer on the immutable home chain or live destination pool. Source split operators can redirect future unlocked allocations but cannot withdraw or reassign existing pending buckets.
- Tenure groups trust the hook's tranche and bucket accounting, which only the registered token and the project's terminals can move. For a direct distributor split, a beneficiary the hook does not track falls back to group 0; direct tenure funding for such a token reverts. The shared collector uses receiver-factory group validation without that split fallback, and source-side prediction does not establish destination pool readiness.
