### A-01 — destination transport refunds

`StickySourceFeePayer.send` calls the selected sucker as the fee child. Every submission through the pinned `JBArbitrumSucker` creates the unsafe root retryable and uses `_msgSender()` as its `excessFeeRefundAddress`; the raw address is preserved. A positive mapped-ERC-20 transfer additionally creates a gateway retryable with `_msgSender()` as its custom refund recipient. The gateway uses the safe Inbox, which rewrites that L1 contract recipient to its L2 alias. The canonical WETH gateway turns the bridged amount into L2 call value and uses the L1 `_from` gateway caller—the source sucker—as `callValueRefundAddress`; cancellation or expiry therefore credits `alias(source sucker)`. A zero-backing ERC-20 send creates no gateway ticket. Any resulting refunds arrive after the source transaction has completed.

Both source retained-credit ledgers can correctly be zero while either destination credit exists. The new destination-only `addFeeRefundToBalance()` operation resolves project 1's current primary native terminal through the canonical directory and has the child contribute its complete raw balance with no caller-selected project, token, amount, terminal or beneficiary. It intentionally does not reimburse the original caller because an asynchronous balance credit carries no payer identity. Terminal failure reverts atomically. The source child still rejects empty-calldata native transfers, so synchronous refunds retain their existing caller attribution. The raw and aliased fee-child excess affects the caller's transport budget, not the leaf's reward principal. The WETH call-value alias is separate and can strand bridged backing principal after cancellation or expiry.

The shared SDK route verifier still rejects Ethereum-to-Arbitrum collector preparation and fails closed on unknown transport. Keep that guard until the reviewed Arbitrum-home family is deployed and the native raw-refund lifecycle passes end to end; keep ERC-20 backing rejected afterward unless its aliased refund is separately resolved.

The installed `toRemote(address)` API cannot accept the original caller as an asynchronous refund beneficiary. The fixed project-1 outcome handles the native root refund without pretending attribution. Current Sticky and Sucker entrypoints control neither `alias(fee child)` nor `alias(source sucker)`, so positive ERC-20 gateway backing still needs upstream explicit destination recipients or a separately reviewed alias-recovery message. Existing registered CCIP routes are a separate alternative: installed CCIP code pays the router its quoted fee and returns excess budget synchronously through the source refund ledger. They require their own route qualification and positive native transport budget; a zero transport payment selects unsupported LINK payment. Other transports require separate qualification; the finding is not a claim that every route to Arbitrum has the same refund behavior. Configurable home-chain identity alone is not transport qualification.

Proofs: `test/audit/SourceFeeArbitrumRefund.t.sol` exercises actual inherited native/ERC-20 transport encoding, proves that the gateway request names the fee child, shows its computed Nitro alias is distinct and verifies the child's fresh-value isolation. Inspection of the pinned `AbsInbox` implementation establishes that the safe Inbox performs the alias rewrite; the local test does not execute the gateway or Inbox rewrite. `StickySourceCollector.t.sol` proves fixed project-1 calldata/value, permissionless execution, destination-chain enforcement, no-op/rollback behavior, reentrancy blocking, direct-transfer rejection and preservation of source refunds. The deployment suite proves that a pre-funded predicted nonce-1 child remains deployable and retains its balance under the correct collector binding. `test_adversarialEthereumToArbitrum_retryableRefundUsesFeeChild` captures the real deployed Inbox payload, deploys the matching Arbitrum-home parent and nonce-1 child on an Arbitrum fork, models the finalized raw ArbOS credit with `vm.deal`, and proves exact live-terminal project-1 accounting with no token mint or caller payment. It separately funds the computed safe-Inbox alias and proves the raw-balance operation leaves that account untouched. It does not execute or prove retryable finality. Production qualification still requires the corresponding verified deployments and end-to-end refund receipt. The separate `test_adversarialEthereumToArbitrum_ccipReturnsSourceTransportRefund` passes against the existing REV CCIP lane: it recreates the committed singleton creation code/arguments to authenticate its complete patched runtime, verifies the registered clone, and uses actual reserves, native wrapping and the deployed router. It proves one exact-fee source submission, source retained-refund attribution and return of the excess budget to the original caller. It does not prove CCIP destination delivery, finality or an Arbitrum Sticky pool.

### A-02 — destination mint readiness

The manual bridge path checks registered reciprocal peers and accounting contexts but can prepare a burn/leaf even when the destination controller already rejects that peer's `mintTokensOf`. Actual destination claims require this mint. Registration alone does not establish current authority; recovery can depend on a source-project authority restoring configuration.

The collector SDK already contained a read-only mint probe. Review of the new native-route mitigation also caught an existing classifier limitation: canonical Arbitrum L2 suckers use a zero L1 Inbox binding. L2 identification must use its actual layer and nonzero gateway rather than incorrectly requiring an L1 Inbox; faithful fixtures and live probes are separate verification gates. Remediation extracts that rule into the SDK's sucker owner, then reuses it with the exact recipient and token amount at manual preparation and the existing reviewed-write revalidation boundary in Sticky, Homerun, Revnet Money and Juicebox Money. A read-only simulation proves present authority, not that authority will remain unchanged during bridge finality.

### A-03 and A-04 — uncertain submissions

The client reproduction models a wallet that sends the reviewed five-token transfer and then loses its response. The prior hook allows a second wallet submission on Retry, which would normally use a new nonce and repeat the transfer; the regression checks wallet-call count and modeled recipient balance. This is a client control-flow proof, not a live transfer. Returning an error with no hash does not establish non-submission. Existing durable launch/bridge journals avoid that sequence; ordinary writes need the same fail-closed boundary across reset, remount and reload.

The separate Safe reproduction advances the Safe's nonce after execution while its service still reports `isExecuted = false`. The prior timeout path labels the proposal replaced without proving which transaction consumed that nonce. Allowing resubmission at that point can repeat a completed operation. Separately, selector-shaped deadline calldata did not establish an enforcing contract: a value transfer to an EOA could be labeled expired from router-shaped calldata while remaining executable. Expiry now needs a canonical, chain-specific enforcing target and numbered-block evidence.

The implemented recovery preserves uncertain writes durably, recovers known hashes/receipts, and releases only on explicit rejection or canonical terminal evidence. It does not infer non-execution from time, missing indexer data or a higher nonce alone. Existing domain journals remain authoritative rather than receiving a second competing lock. These guards operate within the browser origin and saved storage: clearing storage or submitting through another wallet/client is outside their duplicate-prevention boundary. Further adversarial review exercises cross-tab attempt identity, stale asynchronous receipt effects, known hashes that fail persistence, queued Safe call adoption, and historical receipts that must not release a different unknown attempt. New domain attempts carry unique identities, and recovery compares the saved attempt again after asynchronous proof checks. Hashes that cannot yet be saved remain private page-session evidence bound to that exact attempt; recovery retries persistence after storage returns. A full page reload before a hash can be saved loses that memory-only evidence and leaves the durable unknown marker held. A matching historical receipt alone must not unlock it. Revnet activities and batches also require per-record storage so distinct scopes cannot overwrite each other in a shared array.

### A-05 and A-06 — provenance and documentation

The canonical six-suite sync path accepted `kind = simulation` and a receipt with failed status, zero block and no transaction/block hashes. The collector sync path was stricter but relied on canonical source/home configuration. The fix reuses one receipt predicate and requires verified manifests and successful, nonzero, identified receipts. This hardens trusted build inputs; it does not turn local artifacts into independent RPC proof.

Documentation corrections identify historical fixed-route instructions, source-only refund coverage, same-week tranche merging, controller catch-and-burn semantics, receiver implementation parity and the actual forwarder requirement. The same-deployer check against nested Sticky shares is now described accurately: a different factory can wrap transferable shares, leaving their original reward weight in terminal custody. A new regression demonstrates both that reward-weight limitation and recoverable nested principal. JBX itself is not a Sticky share token.

## JBX economics and operational boundaries

- Group 0 is a balance snapshot allocation, not continuous staking remuneration. With unset current/next snapshots, an actor can hold transferable shares across one block, call `poke()`, return them and keep both rounds' proportional rewards. The new proof captures 90% of two pots while having zero tenure entitlement. No redemption tax applies to simply returning transferred shares. The user's no-age preference remains provisional; this consequence must be accepted before launch.
- Receiver arrival does not fix the reward round or recipients. Permissionless settlement can occur after a boundary and benefit a later owner. The new proof makes this explicit.
- A `263157895 / 1e9` reserved split at 38% reserves yields approximately 10% of issuance that participates in reserve accounting. Automatic issuance and bridge remints bypass those reserves. This does not by itself establish a literal 10% of every gross mint or total existing supply. Recheck all applicable current/future stage tables and define the allocation base before execution; the JBP6 allocation is still unchosen.
- JBP6/REV rewards remain JBP6/REV. AutoStick only compounds rewards denominated in the pool's underlying token; it does not exchange those rewards for JBX.
- Permissionless delivery removes recurring Safe custody. It does not install a keeper, supply its fee budget, finalize withdrawals, or guarantee timely settlement. Source authorities must still authorize the initial split configuration.
